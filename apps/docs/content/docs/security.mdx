Sniptide stores ordinary pastes in plain text in Postgres. The server operator can read them,
including private and password-protected pastes. For files and descriptions you want to keep
from the operator, turn on [end-to-end encryption](/core-concepts/encrypted-pastes) when you
create the paste.

## Who can see what

| Who | What they can read |
| --- | --- |
| Anyone with the link | Live public and unlisted pastes, subject to any password, burn-after-read and encryption key requirements. Eligible public pastes also appear on your [profile](/core-concepts/sharing#your-public-profile). |
| People you invite | Live pastes you shared with them, with view or edit access. Signed-in invitees skip the paste password prompt. Burn-after-read pastes still open through the share link, and encrypted pastes still need a key. |
| Your API tokens and agent connections | Your own live ordinary pastes and collections. The [token API](/api-tokens#access) also gives access to your env groups. |
| The server operator | Ordinary paste contents and revisions, metadata for encrypted pastes, and env group values using the server's key. |

The person or team who runs your instance is its operator.
Anyone who can read the database or its backups can read ordinary pastes and their revisions.
Decrypting env group values also requires the server's key.

## Encryption

| Data | Application storage | Notes |
| --- | --- | --- |
| Ordinary paste titles, descriptions, files and revisions | Plain text in Postgres | Visibility, passwords and burn after read control access through the app. |
| Browser-encrypted paste descriptions, file names, languages and contents | AES-256-GCM | Your browser encrypts these before upload and keeps the key. Titles, links and other metadata stay readable to the server. |
| Env group values | AES-256-GCM | Encrypted with a key the server derives from `ENV_SECRETS_KEY` or `BETTER_AUTH_SECRET`. See [Encrypted secrets](/core-concepts/secrets#how-values-are-encrypted). |
| Env group names, variable names and labels | Not encrypted | Only values are encrypted. |

Anyone with the full link to an unlisted encrypted paste has its key. Browser encryption also
depends on the JavaScript your server delivers and the security of your device. See
[what encrypted pastes protect](/core-concepts/encrypted-pastes).

The server can decrypt env group values. Their encryption protects a database dump or backup
while the encryption key stays separate. Disk and volume encryption depend on where Postgres
runs. For self-hosting, configure [HTTPS](/self-hosting/reverse-proxy) and encrypt your
[backups](/self-hosting/backups).

<Callout type="warn">
Store credentials in an [env group](/core-concepts/secrets) if you trust the operator with them.
To share a credential once while keeping it from the server, combine
[browser encryption with burn after read](/core-concepts/encrypted-pastes#combine-it-with-burn-after-read).
</Callout>

## How credentials are stored

| Credential | How Sniptide stores it |
| --- | --- |
| Account password | Hashed with scrypt by Better Auth. The password itself is never stored. |
| Paste password | Hashed with scrypt and a random salt. |
| Env group share link and its password | Only hashes are stored, and every reveal checks the password, expiry and revocation. |
| Personal API token (`snpt_…`) | 32 random bytes, shown once. Only a SHA-256 hash and a short prefix are stored. Tokens can expire after a period you choose, or never. |
| Agent OAuth connection | Codes and tokens are stored as SHA-256 hashes. Codes expire after 10 minutes, access tokens after one hour, and refresh tokens after 30 days without use. Reusing a refresh token ends the connection. See [Token lifetime and revocation](/oauth#token-lifetime-and-revocation). |
| Browser session | A random token in a signed, HTTP-only cookie. The database keeps the token itself with the device's IP address and user agent, which **Settings** shows under signed-in devices. A session lasts seven days and is extended while you use it. |
| GitHub and Google sign-in tokens | Better Auth stores the access and refresh tokens the provider returns. They are **not encrypted** in the database. Sniptide requests sign-in scopes only. |

Protect database access and the cookie-signing secret. Rotating `BETTER_AUTH_SECRET` signs
users out. Follow [Rotate the auth secret](/self-hosting/configuration#rotate-the-auth-secret)
to keep existing env groups readable.

A read-only token can retrieve decrypted env group values through the API, even though the MCP
tool list has no env group tools. Give a token only to clients you trust with your env groups.
Revoke tokens you no longer use under **Settings** > **API tokens**.

## What deletion removes

| Action | What happens | When the data is gone from the database |
| --- | --- | --- |
| Move to trash | The link stops working. You can restore the paste for 30 days. | 30 days later, when the hourly purge job runs |
| Delete forever or empty trash | The paste, its files, revisions, stars, shares and view history are deleted. | At once |
| Expiry passes | The link stops working. You can set a new expiry to bring it back. | On an hourly purge after 30 days |
| Burn after read | The first reveal moves the paste to your trash, where you can restore it as a private paste. | On an hourly purge after 30 days |
| Edit an ordinary paste | Old content can remain in its [revisions](/core-concepts/revisions#what-is-kept). The 20 newest revisions keep a full copy. | When the revision's content ages out or the paste is deleted |
| Delete your account | Your pastes, collections, env groups, tokens and sessions are deleted. | At once |

Burn after read closes the share link after the reveal. The database still holds the paste while
it is in the trash. Select **Delete forever** in **Trash** to remove it sooner.

If you pasted a secret by mistake, editing it out isn't enough, because the earlier revision still
holds it. Delete the paste forever and rotate the secret.

API tokens and agents can move a paste to the trash, but they never delete one for good.

Deletion removes rows from the live database only. Database backups keep deleted pastes until the
backups themselves are deleted, and the operator decides how long that is. Moderation records keep
a removed paste's ID and the reason for the decision, but not its content.

## What the server records about readers

- **View analytics.** Each view, raw read and copy is stored with the referrer's host, the
  country the CDN reports and the device type. The visitor is an HMAC of the IP address and user
  agent under a salt that changes every UTC day. The rollup job deletes old salts from the live
  database after the following day ends. Backups may retain them.
- **Request logs.** [When enabled](/self-hosting/configuration#monitoring), request logs use
  route patterns such as `/[slug]` and record status and duration. A reverse proxy or CDN can
  keep its own logs with full URLs and IP addresses.
- **Product analytics and error tracking.** A configured `POSTHOG_KEY` enables explicit
  analytics events and scrubbed server error reports. Browser analytics have session replay
  disabled. See [monitoring settings](/self-hosting/configuration#monitoring).
- **Instance telemetry.** Self-hosted instances send aggregate usage and deployment information
  by default. See [what instance reports contain and how to turn them off](/self-hosting/configuration#instance-telemetry).

## Treat snippets as untrusted input

A snippet read over [MCP](/mcp) can contain instructions from a gist, a website or a collaborator.
The MCP server labels snippet content as user-provided data and passes it through without a
prompt-injection filter. The agent must treat the content as data. The MCP tools themselves
cannot run code or write local files.

- Use the `read` scope for agents that only look up snippets.
- Keep your client's approval prompts enabled for shell commands and file writes. Review
  proposed changes before an agent applies a snippet or [collection](/core-concepts/collections).
- Limit edit access to people you trust to change the snippets your agents use.

## Run your own instance

With self-hosting, you control operator access and storage.

- Keep `BETTER_AUTH_SECRET` and `ENV_SECRETS_KEY` secret, and store them apart from database
  backups. Anyone holding both a backup and the key can read your env groups.
- Restrict who can reach Postgres and its backups. They hold ordinary pastes in plain text.
- Serve the app over HTTPS only, and consider a [separate share domain](/self-hosting/configuration#separate-share-domain)
  so shared pages run on a different origin than the signed-in app.
- Close sign-up or restrict it to allowed emails with the [sign-in settings](/self-hosting/configuration#sign-in-and-sign-up)
  if the instance isn't meant for the public.
- [Upgrade](/self-hosting/upgrading) when a release fixes a security issue.

## Report a vulnerability

Use [GitHub's private vulnerability reporting form](https://github.com/Dino-Kupinic/sniptide/security/advisories/new).
Include the affected version or URL, reproduction steps and the impact you observed. See the
[disclosure policy](https://github.com/Dino-Kupinic/sniptide/blob/main/SECURITY.md) for scope
and how maintainers handle reports.
