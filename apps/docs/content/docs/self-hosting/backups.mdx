---
title: Backups and restore
description: Back up a self-hosted Sniptide database by hand or on a schedule, check the backup, and restore it into the same or a new server.
---

Everything Sniptide stores (accounts, pastes and revisions, collections, API tokens, analytics)
lives in one Postgres database. A backup is a dump of that database, and a restore loads it back,
into the same server or a new one. The scripts below are in the repository's `scripts/` folder and
are tested in CI: every pull request backs up a seeded instance, upgrades it, and restores the
backup into the running stack and into a brand-new one, checking that nothing was lost.

<Callout type="warn" title="Keep your secrets with the backups">
Keep `BETTER_AUTH_SECRET` to preserve sessions and keep whichever secret encrypted the env group
values: `ENV_SECRETS_KEY` if set, otherwise `BETTER_AUTH_SECRET`. A restore without that encryption
secret still recovers pastes, accounts and API tokens, but the stored env values remain unreadable.
Store the secrets separately from the backup files, which contain password hashes.
</Callout>

## Take a backup

On a Docker Compose install, run the commands from the folder with `docker-compose.yml` and
`.env`. If you used the installer or downloaded just the Compose file, get `scripts/backup.sh`
and `scripts/restore.sh` from the repository at the same tag or branch as your Compose file. Put
them in a `scripts/` folder inside the install directory.

```bash
bash scripts/backup.sh            # writes ./backups/sniptide-<UTC time>.dump
bash scripts/backup.sh /srv/backups
```

The script dumps the database in `pg_dump`'s compressed custom format, checks that the file can be
read back, and prints its path. The file is readable by you alone. Set `BACKUP_KEEP_DAYS=14` to
delete older `sniptide-*.dump` files in that folder at the same time. It is safe to run while
Sniptide is serving traffic: `pg_dump` takes a consistent snapshot.

The script exits with an error and keeps no file when the dump can't be read back, so a printed
path means the backup passed that check. To prove a backup restores, use the
[throwaway restore](#check-a-backup-in-a-throwaway-copy) below.

### Without the script, or with your own Postgres

The script is a thin wrapper over:

```bash
docker compose exec -T db pg_dump -U sniptide -d sniptide \
  --format=custom --no-owner --no-privileges > sniptide.dump
```

Against a Postgres you run yourself, point `pg_dump` at it (use tools at least as new as the server):

```bash
pg_dump --format=custom --no-owner --no-privileges "$DATABASE_URL" > sniptide.dump
```

## Back up on a schedule

For Docker Compose, get `docker-compose.backup.yml` from the same tag or branch and put it beside
`docker-compose.yml`. Include it when you start the stack:

```bash
docker compose -f docker-compose.yml -f docker-compose.backup.yml up -d
```

It runs `pg_dump` at start and then every `BACKUP_INTERVAL_HOURS` (default 24), writes the files
to `./backups` (`BACKUP_DIR`), and deletes the ones older than `BACKUP_KEEP_DAYS` (default 14).
Set the three in `.env`, or `COMPOSE_FILE=docker-compose.yml:docker-compose.backup.yml` so a plain
`docker compose up -d` includes it. Check it with `docker compose logs backup`.

The Compose files stay on the database server. Copy them offsite on a schedule so a disk loss
doesn't take both copies.

## Send Coolify backups offsite

The backup container saves a private dump locally, encrypts a copy with `age`, and sends it to
Backblaze B2. It keeps local dumps for three days, attempts a backup once per UTC day, and retries
failures every 15 minutes. Set a recovery point objective of 24 hours and a recovery time objective
under one hour. Measure both during a [restore drill](#recover-a-lost-coolify-server).

1. On a trusted workstation, run `age-keygen -o sniptide-backup.identity`. Put the identity,
   `BETTER_AUTH_SECRET`, and `ENV_SECRETS_KEY` (if set) in your password manager. Give the
   backup container only the public `age1…` recipient printed by `age-keygen`.
2. Create a dedicated private B2 bucket and [a bucket-restricted write-only application key](https://www.backblaze.com/docs/cloud-storage-s3-compatible-app-keys).
   Store an independent read-only key for recovery. Use the S3 endpoint listed for the bucket.
3. Add [B2 lifecycle rules](https://www.backblaze.com/docs/cloud-storage-lifecycle-rules) by prefix.
   Set **Days From Hiding To Deleting** to `1` for each rule. Cancel incomplete multipart uploads
   after one day. B2 runs cleanup on its schedule.

   | Prefix | Recovery points | Days from upload to hiding |
   | --- | --- | --- |
   | `daily/` | One per UTC day for a week | 7 |
   | `weekly/` | One per ISO week for four weeks | 28 |
   | `monthly/` | One per UTC month for about six months | 184 |
   | `pre-deploy/` | On demand before migrations | 30 |

4. Create a [Healthchecks.io check](https://healthchecks.io/docs/configuring_checks/) with a
   24-hour period and a grace period long enough for the dump and upload. Connect an alert channel.
   The container pings success after all copies due that day upload. A failed run sends `/fail`.
   A stopped container produces a missed heartbeat.
5. Build the backup image on the Docker host from a reviewed Sniptide checkout. Match the client
   major to your database so a dump can be restored into that PostgreSQL major.

   ```bash
   docker build --build-arg POSTGRES_MAJOR=18 -t sniptide-backup:local \
     -f deploy/coolify/backup.Dockerfile deploy/coolify
   ```

   For the Coolify Sniptide Compose template, add the `backup` service and top-level volume from
   `deploy/coolify/backup-sidecar.yaml`. Set the following variables in Coolify and redeploy.

   | Variable | Value |
   | --- | --- |
   | `BACKUP_BUCKET` | Private B2 bucket name |
   | `BACKUP_B2_ENDPOINT` | B2 HTTPS S3 endpoint |
   | `BACKUP_B2_REGION` | Region from the endpoint, such as `us-west-004` |
   | `BACKUP_B2_KEY_ID`, `BACKUP_B2_APP_KEY` | Bucket-restricted writer key ID and secret |
   | `BACKUP_AGE_RECIPIENT` | Public `age1…` recipient |
   | `BACKUP_HEARTBEAT_URL` | Private Healthchecks.io ping URL |

   For a standalone Coolify PostgreSQL resource, put those variables plus `PGHOST`, `PGPORT`,
   `PGDATABASE`, `PGUSER`, and `PGPASSWORD` in a private file on the Docker host. Restrict the
   file to mode `0600`. Use the database's internal hostname and an existing Docker network that
   can reach it. Start the job without a published port.

   ```bash
   docker run -d --name sniptide-backup --restart unless-stopped \
     --network "$BACKUP_NETWORK" --env-file /etc/sniptide/backup.env \
     --mount source=sniptide-backups,target=/backups sniptide-backup:local
   ```

6. Check the container logs for `Uploaded daily/…`, the B2 bucket for the new `.dump.age` object,
   and the monitor for a success ping. Keep the existing backup schedule until you have completed
   an offsite restore drill. Test a missed heartbeat on a staging check with a shorter period.

To take a fresh offsite snapshot before an upgrade, use `docker compose exec -T backup
sniptide-backup pre-deploy` for Compose or `docker exec sniptide-backup sniptide-backup pre-deploy`
for the standalone container. Record the `Uploaded pre-deploy/…` path after the command succeeds.

## Restore

A restore **replaces the whole database** with the backup. It works on a running instance and on a
new one.

On Docker Compose:

```bash
bash scripts/restore.sh backups/sniptide-20261020T120000Z.dump
```

The script asks you to confirm (`--yes` skips the prompt), then it:

1. makes sure the database is up and checks the file is a readable backup, before changing anything;
2. stops the app, so nothing writes while the database is replaced;
3. drops and recreates the database, and loads the backup into it;
4. starts the app, which applies any migrations the backup is missing.

### Into a brand-new server

<Steps>
<Step>

Install Docker, and get `docker-compose.yml`, `scripts/restore.sh` and `.env.example`
(clone the repository, or download them).

</Step>
<Step>

Create `.env` with **the same `BETTER_AUTH_SECRET`** as the old instance (and `ENV_SECRETS_KEY` if
you set one), and `BETTER_AUTH_URL` set to the address the new server will be opened at.

</Step>
<Step>

Copy the backup file over and run `bash scripts/restore.sh sniptide-….dump`.

</Step>
<Step>

Open the instance and sign in. Check a few pastes, and an env group if you use them.

</Step>
</Steps>

A backup from an older Sniptide restores into a newer one: the app migrates it forward when it
starts. Restoring a backup from a **newer** version into an older one isn't supported (see
[Upgrading](/self-hosting/upgrading)).

### Restoring without the script

Stop the app first, so nothing writes while you restore. Then, against an empty database:

```bash
pg_restore --no-owner --no-privileges --exit-on-error --dbname "$DATABASE_URL" sniptide.dump
```

The dump contains `CREATE EXTENSION pg_trgm`, which needs a role allowed to create extensions. If
yours isn't, ask your database operator to create the extension in the empty database first. Start
the app afterwards. On Coolify, run the same commands inside the Postgres container with
`docker exec -i`, as the user Coolify generated for the service.

### Check a backup in a throwaway copy

Restore the dump in a new directory with its own `docker-compose.yml` and `scripts/restore.sh`.
Create a fresh `.env` with the secrets from the backup's original instance and the following
local settings. Use a project name and ports that are free on your machine. Run these commands
from a shell without exported settings for another Compose project.

```dotenv title=".env"
COMPOSE_PROJECT_NAME=sniptide-check
COMPOSE_FILE=docker-compose.yml
COMPOSE_PROFILES=
BETTER_AUTH_URL=http://localhost:3999
SNIPTIDE_BIND=127.0.0.1
SNIPTIDE_PORT=3999
POSTGRES_PORT=55999
```

From that directory, run `docker compose config --services` and check that it lists only `app`
and `db`. This check catches an exported `COMPOSE_PROFILES` or an extra Compose file that would
start other services. Restore the backup:

```bash
bash scripts/restore.sh /path/to/sniptide-backup.dump --yes
```

Sign in at `http://localhost:3999`, open a few pastes, and check an env group if you use them.
Then, from the test directory, run `docker compose down -v` to remove the test containers and
database volume for the project named in that directory's `.env`.

## Recover a lost Coolify server

Run these steps monthly against a throwaway instance. Start a timer before you retrieve the backup.

1. With a read-only B2 key, download the newest daily object to a private directory on a trusted
   machine. Retrieve the `age` identity and app secrets from your password manager. Decrypt the
   object and check the dump with a `pg_restore` client at least as new as the one that made it.

   ```bash
   umask 077
   age -d -i /secure/sniptide-backup.identity -o sniptide.dump sniptide.dump.age
   pg_restore --list sniptide.dump > /dev/null
   ```

2. For a drill, restore the dump with `scripts/restore.sh` using the
   [throwaway Compose setup](#check-a-backup-in-a-throwaway-copy). Pin `SNIPTIDE_IMAGE` to the
   current production digest and use the original auth and encryption secrets. For PostgreSQL 17,
   use the PostgreSQL 17 Compose configuration and a fresh volume. Set `TELEMETRY=off`, omit
   outbound email credentials, and keep the drill on localhost.
3. For a lost server, provision a replacement VPS and Coolify instance. Recreate the PostgreSQL
   resource with the original major, and restore the dump into an empty database. Recreate the app
   resource from the recorded production image digest. Reapply the database connection, app secrets,
   domains, and any OAuth or mail settings from your saved configuration. Start the app and verify
   it through a private route or local host override before pointing production DNS to the new VPS.
   [Configure offsite backups](#send-coolify-backups-offsite) again on the replacement.
4. Check `/api/health`, sign in, open several existing pastes, and verify that an env group decrypts.
   Record the backup timestamp, app digest, elapsed time, and any manual fixes. For a drill, stop
   the scratch project and remove its volumes and decrypted files.

## What a backup doesn't cover

- **Your secrets and settings.** Keep `.env` (or the Coolify variables) with them.
- **The Postgres and app versions.** Restore into the same or a newer supported Postgres major version.
- **Caddy's certificates**, if you use the bundled proxy. They are re-issued automatically.
