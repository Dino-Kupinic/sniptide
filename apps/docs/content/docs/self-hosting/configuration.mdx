title: Configuration
description: Look up every environment variable a self-hosted Sniptide instance reads, with its default, allowed values and effect.
---

Sniptide reads its configuration from environment variables when the server starts. They aren't
built into the image, so a change takes effect when you restart the container, for example with
`docker compose up -d`. The server checks every value at startup and stops with the variable's
name when one is invalid, instead of falling back to a default. A variable that is set but empty
counts as unset.

Only `DATABASE_URL`, `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` need a value, and the Docker
Compose and Coolify templates fill in all three. Every other variable has a default that suits a
small instance, so set one only to turn on a feature or change a limit. The repository's
`apps/web/.env.example` lists the app settings. Docker Compose passes every setting in `.env` to
the app. The Coolify template lists the common ones; see
[Coolify](/self-hosting/coolify#change-settings) to add one it doesn't list.

## Required

| Variable | Default | What it does |
| --- | --- | --- |
| `DATABASE_URL` | none | Postgres connection string, `postgres://user:password@host:5432/sniptide`. Sniptide tests Postgres 17 and 18. Compose runs Postgres 18 and sets this for you. |
| `POSTGRES_VOLUME` | `postgres` | Compose database volume key. Set to `postgres18` when migrating a Postgres 17 installation. See [Upgrading](/self-hosting/upgrading#upgrade-postgres-17-to-18). |
| `BETTER_AUTH_SECRET` | none | Signs sessions and supplies the default key for env group values. Generate with `openssl rand -hex 32` and keep it across restarts. Changing it signs everyone out. See [Rotate the auth secret](#rotate-the-auth-secret) if you store env groups. |
| `BETTER_AUTH_URL` | none | The exact URL people open in the browser (`https://…` behind a proxy). The app boots without it, but sign-in and sign-up are rejected from any other origin ("Invalid origin"), and OAuth callbacks and printed links use it. |

## Edition

| Variable | Default | What it does |
| --- | --- | --- |
| `SNIPTIDE_EDITION` | `selfhost` | Leave this set to `selfhost` for your own instance. Pages and raw share links send `X-Robots-Tag: noindex, nofollow, noarchive`. Sniptide Cloud uses `cloud`, which enables public discovery and supports the template gallery. |

Self-hosted public links can still be opened by anyone who has the address. Search engines can
fetch the pages to read the noindex directive. Use a [private paste](/core-concepts/sharing#choose-a-visibility)
to control who can open a link.

## Sign-in and sign-up

| Variable | Default | What it does |
| --- | --- | --- |
| `ALLOW_SIGN_UP` | `true` | `false` closes sign-up for everyone, and `first` closes it once the first account exists. Existing accounts keep signing in. It wins over `ALLOWED_EMAILS`. The install script and the Coolify template set `first`. |
| `ALLOWED_EMAILS` | unset | Comma-separated emails that may sign up (invite-only). New password accounts need SMTP email verification before signing in; without SMTP, only verified OAuth identities can join. Existing accounts keep signing in. |
| `HOME_URL` | unset | The logo on the sign-in screens links here, for example to your landing page. Unset, the logo is not a link. |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | unset | Turn on GitHub sign-in and the GitHub integration in **Settings**. Until both are set the sign-in button shows as disabled and the integration as not set up. Callback URL: `<BETTER_AUTH_URL>/api/auth/callback/github`. The integration comes back to a path below it, so one OAuth app serves both. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | unset | Turn on Google sign-in. Callback URL: `<BETTER_AUTH_URL>/api/auth/callback/google`. |
| `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET` | unset | Turn on the Slack integration in **Settings**, which sends pastes to channels. Until both are set it shows as not set up. See [Set up the Slack integration](#set-up-the-slack-integration). |
| `SLACK_SIGNING_SECRET` | unset | Turns on previews of Sniptide links shared in a Slack workspace that connected Sniptide. Without it the events URL answers 404. See [Set up the Slack integration](#set-up-the-slack-integration). |
| `LINEAR_CLIENT_ID`, `LINEAR_CLIENT_SECRET` | unset | Turn on the Linear integration in **Settings**, which attaches pastes to issues. See [Set up the Linear integration](#set-up-the-linear-integration). |
| `NOTION_CLIENT_ID`, `NOTION_CLIENT_SECRET` | unset | Turn on the Notion integration in **Settings**, which saves pastes as pages. See [Set up the Notion integration](#set-up-the-notion-integration). |
| `BETTER_AUTH_TRUSTED_ORIGINS` | unset | Extra origins allowed to call the auth API, comma-separated, besides `BETTER_AUTH_URL`. |
| `COOKIE_DOMAIN` | unset | Share the session cookie with other subdomains. Leave unset on one domain. |
| `COOKIE_PREFIX` | `better-auth` | Prefix for the auth cookies' names (letters, digits, `-`, `_`). Set a different one on a deployment that shares a parent domain with another one (a preview next to production). Changing it signs everyone out. |
| `DEMO_MODE` | `false` | A public demo: every visitor is signed in to one shared guest account with example data, reset on a schedule. The workspace uses the regular app layout without a demo banner. The welcome paste explains the shared account and resets. Pastes made in the demo are visible to every visitor and deleted at the next reset. Every page answers with `X-Robots-Tag: noindex, nofollow`, so search engines leave the demo out. Use it with `ALLOW_SIGN_UP=false` so the guest is the only account. |
| `DEMO_RESET_MINUTES` | `60` | With `DEMO_MODE`, minutes between resets (5 to 1440). The guest is also reset at server start. |

Existing email and password accounts keep signing in. Pending invitations remain blocked until
their email is verified, even if the invite list or SMTP is later disabled. See also
[closing sign-up](/getting-started/self-hosted#close-sign-up-for-a-private-instance).

GitHub and Google sign-in require your own OAuth app credentials and the callback URLs listed
above.

## Pastes and sharing

| Variable | Default | What it does |
| --- | --- | --- |
| `MAX_PASTE_SIZE` | `1MB` | The most one paste can hold, across its files. Plain bytes or a number with a unit (`B`, `KB`, `MB`, `GB`, binary: 1 KB = 1024 bytes): `1MB`, `512KB`, `1.5MB` and `1048576` all work. |
| `SHARE_URL` | unset | Domain share links use when it differs from the app's. Use a domain you control or leave it unset to serve everything on one domain. |
| `SHARE_PROXY_SECRET` | unset | Shared with a separate share-domain site that proxies share pages to the app, so it can pass the visitor's IP. |
| `GITHUB_TOKEN` | unset | A GitHub token (no scopes needed) for gist imports by accounts that haven't connected GitHub. Without it they share GitHub's unauthenticated quota of 60 requests an hour. |
| `SLACK_WEBHOOK_URL`, `DISCORD_WEBHOOK_URL` | unset | Incoming webhooks that **Share via…** posts paste links to. One channel per provider. Every paste owner on the instance can post to it, 20 times an hour per account. Keep the URLs secret. |
| `ENV_SECRETS_KEY` | unset | Secret of at least 32 characters from which Sniptide derives the encryption keys for env group values and for the tokens of connected integrations. When unset, Sniptide derives them from `BETTER_AUTH_SECRET`. |

### Set up the Slack integration

The Slack integration needs a Slack app of your own, because a Slack app's redirect URLs belong
to one server.

1. Create an app at [api.slack.com/apps](https://api.slack.com/apps), from scratch, in any
   workspace. Under **Manage Distribution**, allow installs in other workspaces if your users
   work in more than one.
2. Under **OAuth & Permissions**, add the redirect URL
   `<BETTER_AUTH_URL>/api/integrations/slack/callback`. Slack requires HTTPS.
3. Add the bot token scopes `chat:write`, `chat:write.public`, `channels:read`, `groups:read`,
   `links:read` and `links:write`.
4. Copy the **Client ID** and **Client Secret** from **Basic Information** into
   `SLACK_CLIENT_ID` and `SLACK_CLIENT_SECRET`, and restart Sniptide.

Leave PKCE off for the app. Sniptide keeps the client secret on the server, and Slack accepts
PKCE only from apps that give it up.

To preview Sniptide links in Slack, also do the following.

1. Copy the **Signing Secret** from **Basic Information** into `SLACK_SIGNING_SECRET` and
   restart Sniptide.
2. Under **Event Subscriptions**, turn events on and set the request URL to
   `<BETTER_AUTH_URL>/api/integrations/slack/events`. Slack checks it right away.
3. Under **App unfurl domains**, add the domain of your share links: the host of `SHARE_URL`, or
   of `BETTER_AUTH_URL` when it is unset.
4. Subscribe to the bot event `link_shared`.

A workspace connected before you added the link scopes has to connect again in **Settings**
before its links get previews.

### Set up the Linear integration

1. Create an OAuth application under **Settings**, **API** in Linear.
2. Add the callback URL `<BETTER_AUTH_URL>/api/integrations/linear/callback`.
3. Copy the client ID and client secret into `LINEAR_CLIENT_ID` and `LINEAR_CLIENT_SECRET`, and
   restart Sniptide.

Sniptide asks for the `read` and `issues:create` scopes. It reads the open issues a user is
assigned to or created, and creates attachments on them.

### Set up the Notion integration

1. Create a public integration at
   [notion.so/profile/integrations](https://www.notion.so/profile/integrations).
2. Add the redirect URI `<BETTER_AUTH_URL>/api/integrations/notion/callback`.
3. Under **Capabilities**, allow reading and inserting content.
4. Copy the OAuth client ID and client secret into `NOTION_CLIENT_ID` and
   `NOTION_CLIENT_SECRET`, and restart Sniptide.

When a user connects, Notion asks which pages Sniptide may use. Sniptide only sees those pages
and saves new pages inside them.

### Rotate the auth secret

Keep the secret that protects your existing env groups. If `ENV_SECRETS_KEY` is already set, keep
its current value when you change `BETTER_AUTH_SECRET`. If it is unset and the old auth secret is
still safe to keep, set `ENV_SECRETS_KEY` to the **exact old value** of `BETTER_AUTH_SECRET`
(at least 32 characters) and set the new `BETTER_AUTH_SECRET` in the same deployment. After
restarting, sign in again and check that an existing env group can still be read.

To retire the old encryption secret, have each group owner save a secure copy of their values
before changing the key, for example with [the CLI](/cli#sync-env-files). After deploying the
new key, push the saved groups again and verify that their values can be read. A database dump
contains encrypted values, so keep the original secret with any backups taken before the change.

Integration tokens use the same secret. After it changes, connected integrations show as not
connected, and their owners connect them again in **Settings**.

### Separate share domain

To serve share links on their own domain, such as `paste.example` next to `app.paste.example`:

1. Point the share domain at the same container as the app.
2. Set `SHARE_URL` to the share domain's HTTPS address and restart the app.
3. If another site proxies the share domain, route `/secret-share/*` to the app as well as paste
   links.

Copied links then use the share domain. Share pages and raw files stay on it, and app pages
opened there redirect to `BETTER_AUTH_URL`. Open a copied link to check that it loads the paste.

## Email

Notification emails are off until you configure SMTP. In-app notifications and password sign-in
work without it. Set the host and sender together, plus `BETTER_AUTH_URL` and a
`BETTER_AUTH_SECRET` of at least 32 characters. Users verify their address and opt in per event in
**Settings** > **Notifications**.

The same SMTP settings enable password reset emails. Without SMTP, the forgot-password page asks
people to contact the administrator.

With SMTP, each new account also gets one welcome email after its first sign-in. It links to the
editor, the [MCP server](/mcp), the [CLI](/cli) and Settings. Invited accounts get it after they
verify their email. Accounts that existed before the welcome email was added never get one, and
demo instances never send it. Set `WELCOME_EMAIL=false` to turn it off.

Every email goes out as HTML with a plain-text version that carries the same sentences and links.
The HTML follows the reader's light or dark appearance in clients that support it, such as Apple
Mail. Gmail and Outlook on the web apply their own dark mode instead. The only images are the
Sniptide logo, which email clients load from `<BETTER_AUTH_URL>/email/`, so that address must be
reachable from the internet for the logo to show. Clients that block images show the name instead.
Clients that load web fonts, such as Apple Mail, also take Archivo and Inter from the same address,
and the rest use the system fonts.

Emails are written in the reader's language: English, German, Spanish, Japanese or Simplified
Chinese. Account emails, such as a password reset, use the language of the browser that asked for
them. Notification emails use the language the person last picked in Sniptide, or the one they were
using when they turned on an email, and English before either happens.

| Variable | Default | What it does |
| --- | --- | --- |
| `SMTP_HOST`, `SMTP_FROM` | unset | Server and sender address. Both are needed. |
| `SMTP_PORT` | `587`, or `465` with `SMTP_SECURE=true` | The server's port. |
| `SMTP_USER`, `SMTP_PASSWORD` | unset | Credentials; supply both or neither. |
| `SMTP_SECURE` | `true` on port 465, `false` otherwise | `true` for implicit TLS. |
| `SMTP_REQUIRE_TLS` | `true` | Require STARTTLS otherwise. Only set `false` for a trusted local test server. |
| `WELCOME_EMAIL` | `true` | Send new accounts one welcome email after their first sign-in. Needs SMTP. |
| `NOTIFICATION_EMAIL_CONCURRENCY` | `2` | How many notification emails are sent at once, 1 to 10. |

### Product update emails

An instance can also send release notes and news to people who turn on **Product updates** in
**Settings** > **Notifications**. These go through [Resend Broadcasts](https://resend.com/features/broadcasts)
instead of SMTP, because Resend handles each reader's unsubscribe link, bounces and complaints.
Without the two variables below, Settings doesn't show the switch and the instance never contacts
Resend.

| Variable | Default | What it does |
| --- | --- | --- |
| `RESEND_API_KEY` | unset | A Resend API key with full access. With `RESEND_SEGMENT_ID`, turns on product update emails. |
| `RESEND_SEGMENT_ID` | unset | The Resend segment that holds the subscribers. |
| `BROADCAST_FROM` | unset | The sender of broadcasts, such as `Sniptide <updates@news.example.com>`. |
| `BROADCAST_SENDERS` | unset | Comma-separated email addresses of the accounts that may write and send product updates. Needs `RESEND_API_KEY`, `RESEND_SEGMENT_ID` and `BROADCAST_FROM`. |

Sniptide keeps the segment in step: turning the switch on subscribes the verified address, turning
it off unsubscribes it, an email change moves it, and deleting the account deletes the contact.
Unsubscribing through a broadcast's link is recorded in Resend only, so Settings keeps showing
the switch as on. Send from a subdomain of
your own, so a complaint about a broadcast can't affect password reset and notification emails.

An account listed in `BROADCAST_SENDERS` with a verified address sees **Write update** in
**Settings** > **Notifications**, which opens **Product updates**. There it writes each update in
Markdown, with a subject, a preview line, a cover label and an optional screenshot link, and sees
the finished email beside the form as it types. Drafts save on their own. **Send test to me**
sends one copy to the writer's address, and **Send to subscribers** asks for confirmation and then
sends the update to the whole segment at once. A sent update stays in the list as a record and can
no longer change, and sending the same update twice is refused.

A screenshot link must use https and point to an image at least 700px wide. Sending to subscribers
also needs `OPERATOR_NAME` and `OPERATOR_ADDRESS`, because the email names its sender, and
`BETTER_AUTH_URL` for the logo and links. Updates are written and sent in one language.

### Email delivery

Email runs independently once a minute and uses a durable queue with bounded retries. Events older
than 24 hours are skipped, including events queued while SMTP was unavailable. Delivery rechecks
consent and access, and messages contain generic activity text with links to the signed-in app.
Each email includes a confirmation link that stops only that event's emails. Opening it does not
change preferences. Email is delivered at least once when retries succeed; a crash after SMTP
acceptance and before recording success can cause a duplicate. A concurrent access change can
still allow an already sending generic email to arrive.

## Database and capacity

Each process uses its configured pool and can open one dedicated live-update listener. Budget for
replicas × (pool size + 1), plus migration and admin connections, within Postgres' connection limit.
Invalid values stop the server with the allowed range.

| Variable | Default | Range | What it does |
| --- | --- | --- | --- |
| `DATABASE_POOL_SIZE` | `10` | 1 to 100 | Connections per process. |
| `HTTP_ADMISSION_LIMIT` | `64` | 1 to 1024 | Active ordinary dynamic requests per process. Excess requests receive 503. |
| `PROBE_ADMISSION_LIMIT` | `2` | 1 to 16 | Active health and metrics requests. |
| `LIVE_ADMISSION_LIMIT` | `128` | 1 to 4096 | Active live-update streams, separate from ordinary requests. |
| `DATABASE_PROBE_RESERVE` | `1` | 1 to 16 | Reserved database execution capacity for probes. |
| `DATABASE_MAINTENANCE_RESERVE` | `1` | 1 to 16 | Reserved database execution capacity for background jobs. |
| `DATABASE_ADMISSION_QUEUE_LIMIT` | `64` | 0 to 4096 | Maximum waiting database submissions per process. |
| `VISIT_DRAIN_BATCH_SIZE` | `500` | 1 to 5000 | Maximum ordinary visits applied per drain batch. |
| `VISIT_QUEUE_MAX_LAG_MS` | `30000` | 1000 to 3600000 | Pending-visit age that triggers temporary backpressure. |
| `VISIT_QUEUE_MAX_BACKLOG` | `10000` | 1 to 1000000 | Sampled pending-visit count that triggers temporary backpressure. |
| `DATABASE_CONNECT_TIMEOUT_SECONDS` | `10` | 1 to 120 | Opening a database connection. |
| `DATABASE_IDLE_TIMEOUT_SECONDS` | `20` | 1 to 3600 | Retire idle connections. |
| `DATABASE_MAX_LIFETIME_SECONDS` | `1800` | 60 to 86400 | Recycle connections. |
| `DATABASE_STATEMENT_TIMEOUT_MS` | `10000` | 100 to 300000 | SQL execution deadline. |
| `DATABASE_LOCK_TIMEOUT_MS` | `3000` | 100 to 300000 | Lock wait deadline. |
| `DATABASE_IDLE_TRANSACTION_TIMEOUT_MS` | `15000` | 100 to 300000 | Abandoned-transaction deadline. |
| `ACCOUNT_STORAGE_BYTES` | `100MB` (100 MiB) | Positive size in bytes or with a unit, or `unlimited` | Per-account paste content budget, trash included. |
| `ACCOUNT_PASTE_LIMIT` | `1000` | Positive whole number or `unlimited` | Per-account paste count, trash included. |
| `VIEW_HISTORY_RETENTION_DAYS` | `90` | 60 to 3650 | Daily view history kept for the charts. |
| `ANALYTICS_RETENTION_DAYS` | `180` | 180 to 3650 | Daily analytics rollups kept. |
| `PURGE_BATCH_SIZE` | `500` | 1 to 5000 | Most rows deleted per batch by the hourly cleanup. |
| `PURGE_TIME_BUDGET_MS` | `2000` | 100 to 60000 | How long one cleanup run may keep starting new batches. |
| `ANALYTICS_ROLLUP_TIME_BUDGET_MS` | `2000` | 100 to 60000 | How long one analytics rollup run may keep starting new batches. |
| `HIGHLIGHT_CACHE_BYTES` | `33554432` | 0 to 256 MiB | Syntax-highlight cache per process; `0` turns it off. |
| `SLOW_QUERY_MS` | `500` | 1 to 60000 | Threshold for slow-query log events. |
| `REQUEST_LOG` | `all` | `all`, `errors`, `off` | Which requests get a JSON log line. `errors` logs 5xx and aborted responses only. Metrics count every request. |
| `MIGRATIONS_DIR` | set by the image | n/a | Where migrations are read from at startup. Leave unset outside the image. |

Set either account limit to `unlimited` or `0` to remove that limit. Trash and expired pastes are
removed after 30 days by a cleanup that runs at startup and hourly.

## Monitoring

| Variable | Default | What it does |
| --- | --- | --- |
| `METRICS_TOKEN` | unset | Operator credential for `GET /api/metrics` and `POST /api/jobs/{name}` maintenance writes. Metrics include latency, query counts, memory, event-loop delay, database size, and job success/failure/overdue state. Jobs are `purge`, `analytics`, `usage`, `email`, and `telemetry`. Without a token both endpoints return 404. Keep it in an operator secret store, restrict access, and scrape every replica. Job status is per process and resets on restart. |
| `POSTHOG_KEY`, `POSTHOG_HOST` | unset, `https://us.i.posthog.com` | PostHog product analytics and server [error tracking](#error-tracking), off unless a key is set. Cookieless, no session replay, events never include paste content or links' slugs. Cookieless events carry the visitor's country only when a CDN in front of the app sends one (`CF-IPCountry`, `X-Vercel-IP-Country` or `CloudFront-Viewer-Country`), because PostHog drops the IP of cookieless events before its GeoIP lookup. `POSTHOG_HOST` picks the region (`https://eu.i.posthog.com` for the EU). Preview deployments and local development get no browser key. |

The Analytics page inside the app counts views, copies and referrers in your own database; nothing
is sent anywhere else.

### Instance telemetry

Your instance sends a daily usage report to Sniptide by default. To stop collection and delivery,
set `TELEMETRY=off` and restart every replica. Your own product analytics and error tracking
use the separate `POSTHOG_KEY` setting.

| Variable | Default | What it does |
| --- | --- | --- |
| `TELEMETRY` | `on` | Sends daily instance reports to Sniptide. `off` skips collection and delivery. |
| `TELEMETRY_ID` | derived from the auth secret | Optional random UUID for the installation identity. Generate one with `node -e 'console.log(crypto.randomUUID())'`. Changing it resets the identity for future reports. Use the same value on every replica. |
| `TELEMETRY_DEPLOYMENT` | `other` | Deployment label: `docker`, `coolify` or `other`. The official image sets `docker`; the Coolify template sets `coolify`. |

Reports go to `https://app.sniptide.com/api/instance-telemetry` and are stored in Sniptide's
PostHog project. Delivery is attempted at most once per day for replicas sharing a database and
has a three-second timeout. Check the `telemetry` job in the protected metrics endpoint for status.
Demo instances skip reporting.

Each report includes:

- A stable installation ID. Without `TELEMETRY_ID`, the app derives it from
  `BETTER_AUTH_SECRET` without sending the secret. Set a new ID for a cloned instance if you
  want its reports to be treated separately.
- The release, deployment type, operating system, architecture and Node.js major version.
- Account totals and active-account counts, grouped activity totals for web, API, CLI and MCP,
  and the dates when observation and paste creation began.
- Bucketed paste, collection, API request, memory and uptime counts, plus flags for configured
  sign-in providers, email, Slack, Discord and the support assistant.

Account identifiers and individual activity rows stay in your database. Reports omit paste
content, titles, links, credentials, raw logs and your instance address. Sniptide receives the
source IP as part of the HTTPS connection and uses an HMAC of it for rate limiting. It does not
forward the IP or request headers to PostHog. Delivery logs can include connection metadata.

The receiving PostHog project controls retention. Turning off telemetry or changing the
installation ID does not delete reports already sent.

### Error tracking

With `POSTHOG_KEY` set, the server also sends its exceptions to PostHog error tracking in the same
project: errors in pages, route handlers, server actions and the proxy, and failures in the
maintenance jobs, the visit queue and the demo reset. Without a key no exceptions are sent, and
exceptions only reach the server log as before. Preview deployments and `localhost` never report.

Multipart POST requests to pages require the `Next-Action` header sent by the browser client.
Without it, Sniptide returns `400 Bad Request` before the page renderer decodes the body.

Each exception carries the route file (such as `app/[slug]/page`, never the visited path), the
release from `DEPLOYMENT_VERSION`, the runtime, the request method or the job's name, and Next's
error digest. Before an exception leaves the server, Sniptide removes:

- Quoted values in the message, which is where paste content, slugs and other input appear.
- A failed query's parameters and Postgres key details.
- Email addresses, API tokens, bearer credentials, JWTs and long random strings.
- URL paths beyond their route, query strings and fragments, in the message and in stack frames.
- Every other property of the error object, such as a request or a query.

Each server process sends at most 30 exceptions a minute and waits at most 3 seconds for PostHog,
so a failure loop can't flood the project or slow down responses. Errors in the browser are not
sent.

To get notified, add alerts in PostHog's error tracking settings on the issue created and issue
spiking triggers, and send them to Slack, Linear, GitHub or a webhook.

## Support and feedback

**Feedback** in the account menu works without any of these settings: it opens a prefilled
GitHub issue at `HELP_URL`, and no report is sent automatically. Set the Linear variables to
receive reports in your own tracker, and an Anthropic key to add the support assistant. See
[Get help and report a bug](/support) for what people see and what each report contains.

| Variable | Default | What it does |
| --- | --- | --- |
| `LINEAR_API_KEY` | unset | A Linear API key that can create issues and upload files. With `LINEAR_TEAM_ID`, reports are sent from the server and filed as Linear issues. |
| `LINEAR_TEAM_ID` | unset | The team to file in, by key or ID. Reports land in the team's Triage state when triage is on, with its `Bug` or `Feedback` label when one exists. Bugs start at Medium priority and feedback without one. |
| `LINEAR_PROJECT_ID` | unset | The ID of a project to add every report to. |
| `ANTHROPIC_API_KEY` | unset | Turns on the **Ask** tab with Claude. Each question sends the docs, the conversation and the report details to Anthropic's API, billed to this key. With the Linear settings, the assistant can also file reports. |
| `OPENAI_API_KEY` | unset | Turns on the **Ask** tab with an OpenAI model instead. It sends the same data to OpenAI's API, billed to this key, and needs `SUPPORT_MODEL`. |
| `SUPPORT_PROVIDER` | the provider whose key is set | `anthropic` or `openai`. Needed only when both keys are set, because Anthropic is used otherwise. |
| `SUPPORT_MODEL` | `claude-haiku-5-5` with Anthropic, none with OpenAI | The model the assistant uses, such as a Claude model ID or an OpenAI model ID. The docs come first in every request, so both providers can reuse their prompt cache for repeat questions instead of paying full price for the docs again. |

Each account can send 10 reports an hour and ask 10 questions a day,
with each question limited to 300 characters. The daily count resets 24 hours after the account's
first question of the period. A report that repeats an open issue,
the same kind of report from the same page with the same opening words, becomes a comment on that
issue. Failures are logged as `support:` lines in the server log.

## Build-time settings

These are Docker build arguments for people building the image themselves, not runtime settings.
`DEPLOYMENT_VERSION` (a commit SHA) sets Next's deployment id, so all replicas of a release agree.
For independently built replicas, a stable Server Actions key can be passed as a BuildKit secret,
`server_actions_key`. You don't need either when running the published image.
