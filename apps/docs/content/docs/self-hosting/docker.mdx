Use this route when you already run Postgres and want only the Sniptide container. To run the
database too, use [Docker Compose](/self-hosting/docker-compose).

## Before you begin

- Postgres 17, which Sniptide is built and tested against, with an empty database for Sniptide.
- A database user that can create tables and the `pg_trgm` extension. The first migration installs
  `pg_trgm` for title and link search. If your provider doesn't allow that, ask the database
  operator to run `CREATE EXTENSION pg_trgm;` in the database first.
- The database host must be reachable from inside the container. `localhost` inside the container
  is the container itself, not your server.

## Create the settings file

Create `sniptide.env` and keep it out of source control:

```dotenv title="sniptide.env"
DATABASE_URL=postgres://user:password@your-postgres-host:5432/sniptide
BETTER_AUTH_SECRET=replace-with-a-long-random-secret
BETTER_AUTH_URL=http://localhost:3000
```

- Generate the secret with `openssl rand -hex 32` and keep it across restarts.
- Set `BETTER_AUTH_URL` to the exact address people open in the browser. Behind a reverse proxy,
  that is the public `https://` address.

## Run the container

```bash
docker run -d --name sniptide --restart unless-stopped \
  -p 3000:3000 --env-file sniptide.env ghcr.io/dino-kupinic/sniptide:latest
```

The container applies its migrations and then serves on port 3000.

## Check that it works

```bash
curl http://localhost:3000/api/health
```

The response is `{"ok":true}` when the app reaches the database, and `{"ok":false}` with status
`503` when it doesn't. If the container exits, `docker logs sniptide` names the setting or the
migration that failed. See [Troubleshooting](/troubleshooting#self-hosted-instances).
