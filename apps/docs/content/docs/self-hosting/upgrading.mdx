This page upgrades a running instance to a newer Sniptide release. Sniptide migrates its database
when the new version starts, so an upgrade is a backup, an image change and a check.

<Callout type="warn">
Back up your database before every upgrade. Downgrading isn't supported, so the backup is your way
back. See [Backups and restore](/self-hosting/backups).
</Callout>

## Before you upgrade

1. **Back up the database** and keep the dump off this server. Use the instructions for your
   installation in [Backups and restore](/self-hosting/backups#take-a-backup).
2. **Read the release notes** for the versions you are skipping, on the project's GitHub releases
   page. A release that needs an action from you says so under **BREAKING CHANGES**.
   See [Versions and releases](/self-hosting/versions).
3. **Keep the previous image's tag** so you know what you came from.
4. If the migration role is restricted, make sure the `pg_trgm` extension is installed, because
   the migrations need it. See [Docker](/self-hosting/docker#before-you-begin).
5. On a database with many pastes, some migrations create indexes and backfill data inside the
   migration transaction, which can block writes. Plan the upgrade for a quiet time and watch the
   database while it runs. A very large instance (on the order of 100,000 pastes) should schedule a
   window.

## How the upgrade runs

Sniptide applies its own database migrations when it starts, before it serves requests. There is no
separate migration command. Migrations are written to be additive (new tables and columns) where
possible, so the old container keeps serving until the new one is healthy. All pending migrations
run in one transaction under a lock, so two containers starting together take turns.

Skipping releases is expected to work, since every migration the database is missing is applied in
order. What CI exercises on every pull request is the step from the latest release to the next one
(see [Versions and releases](/self-hosting/versions)).

## Upgrade the instance

<Tabs items={["Docker Compose", "Docker", "Coolify"]}>
<Tab value="Docker Compose">

```bash
docker compose pull
docker compose up -d
```

Compose uses `latest` by default. For repeatable deployments, pin a release in `.env`:

```dotenv title=".env"
SNIPTIDE_IMAGE=ghcr.io/dino-kupinic/sniptide:1.2.3
```

Replace `1.2.3` with a release from the GitHub releases page, or pin an image digest. Upgrading
is then a deliberate edit of that line followed by `docker compose pull && docker compose up -d`.

</Tab>
<Tab value="Docker">

Set `version` to the release tag you want, then pull the image and replace the container.
This example uses the port and env file from the [Docker guide](/self-hosting/docker).
Carry over any other options you set on your container.

```bash
version='1.2.3' # Replace with your target release tag.
image="ghcr.io/dino-kupinic/sniptide:$version"
docker pull "$image" &&
  docker stop sniptide &&
  docker rm sniptide &&
  docker run -d --name sniptide --restart unless-stopped \
    -p 3000:3000 --env-file sniptide.env "$image"
```

</Tab>
<Tab value="Coolify">

Redeploy the service so it runs the newer image. If you run `latest`, make sure the redeploy pulls
it; pinning a version tag in the service makes the change explicit.

</Tab>
</Tabs>

## Verify the upgrade

```bash
curl https://paste.example.com/api/health
```

The response is `{"ok":true}` when the server is up and the database answers. Then sign in and
open a paste. On startup the app logs a `migrations` line listing the migrations it applied, which is
empty when the database was already current.

## Recover from a failed upgrade

### Duplicate provider account identities

The ownership integrity migration adds a unique index on `account(provider_id, account_id)` and
a foreign key that keeps each paste in one of its owner's collections. It locks the account,
paste and collection tables while it checks existing data and adds the constraints, so schedule
this upgrade for a quiet time.

Pastes pointing at collections that no longer exist are taken out of those collections. Their
contents and revisions are kept, and their edit versions advance so an older editor cannot
overwrite the change.

If startup reports `Duplicate provider account identities`, the migration rolls back without
changing any data. Connect to the database with your SQL client and inspect the duplicate keys:

```sql
SELECT provider_id, account_id, count(*)
FROM account
GROUP BY provider_id, account_id
HAVING count(*) > 1;
```

Review the matching account rows and their `user_id` values before repairing them. Different
users must stay separate: do not automatically merge users or delete their account records.
Once each provider identity belongs to exactly one account row, retry the upgrade. The query
above should return no rows, and startup should report the migration as applied. See
[Better Auth's account identity guidance](https://www.better-auth.com/docs/guides/1-7-upgrade-guide#check-for-duplicate-account-keys).

### Other upgrade failures

**The upgrade fails to start.** Migrations run in a single transaction, so a failed upgrade rolls
back completely and leaves the database exactly as it was before you started; it is never
half-migrated. The new container doesn't become ready, and the log says which migration failed.
Fix the cause (database access, or a missing extension) and start it again, or go back to the
previous image, which still matches the database.

**You want to go back after a successful upgrade.** Downgrading isn't supported, because the older
code doesn't know the newer schema. Restore the backup you took before upgrading
(see [Backups and restore](/self-hosting/backups)), then run the older image. If you start an older
image against a newer database anyway, it runs, but logs a `migrations_ahead` warning naming the
migrations it doesn't know.

## Upgrade several replicas

If you run more than one replica, build once and deploy the exact same image to all of them, and
remember that each process holds its own database pool: replicas × `DATABASE_POOL_SIZE` (twice
that while two releases overlap) must fit the database's connection budget. Drain old instances
before removing the previous image.
