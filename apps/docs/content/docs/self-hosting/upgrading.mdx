<Callout type="warn">
Back up your database before every upgrade. See [Backups](/self-hosting/backups).
</Callout>

## What happens on upgrade

Sniptide applies its own database migrations when it starts, before it serves requests. There is no
separate migration command. Migrations are written to be additive (new tables and columns) where
possible, so the old container keeps serving until the new one is healthy.

If a migration fails, it rolls back and the new container does not become ready, so you are never
left with a half-migrated app serving traffic. Fix the cause (for example database access) and
start it again.

## Docker Compose

```bash
docker compose pull
docker compose up -d
```

Compose uses `latest` by default. For repeatable deployments, pin a release in `.env`:

```dotenv
SNIPTIDE_IMAGE=ghcr.io/dino-kupinic/sniptide:1.2.3
```

(substitute an actual release), or pin an image digest. Upgrading is then a deliberate edit of that
line followed by `docker compose up -d`.

## Docker

Pull the new image, then replace the container with the same options:

```bash
docker pull ghcr.io/dino-kupinic/sniptide:<version>
docker stop sniptide && docker rm sniptide
docker run -d --name sniptide … ghcr.io/dino-kupinic/sniptide:<version>
```

## Coolify

Redeploy the service so it runs the newer image. If you run `latest`, make sure the redeploy pulls
it; pinning a version tag in the service makes the change explicit.

## Before you upgrade

1. **Back up the database.**
2. **Keep the previous image** (or its tag) so you can go back to it.
3. If the migration role is restricted, make sure the `pg_trgm` extension is installed; the early
   growth migration needs it. See [Docker](/self-hosting/docker#about-the-database).
4. On a database with many pastes, some migrations create indexes and backfill data inside the
   migration transaction, which can block writes. Plan the upgrade for a quiet time and watch the
   database while it runs. A very large instance (on the order of 100,000 pastes) should schedule a
   window.

## Check it worked

```bash
curl http://<your-address>/api/health
```

returns `{"ok":true}` when the server is up and the database answers. Then sign in and open a
paste.

## Going back

Because migrations are additive where possible, the previous image generally runs against the
upgraded database, but that is not guaranteed for every release. If an upgrade goes wrong, the
safe path is to restore the backup you took before it. The restore procedure is being defined:
see [Backups](/self-hosting/backups).

## Replicas

If you run more than one replica, build once and deploy the exact same image to all of them, and
remember that each process holds its own database pool: replicas × `DATABASE_POOL_SIZE` (twice
that while two releases overlap) must fit the database's connection budget. Drain old instances
before removing the previous image.
