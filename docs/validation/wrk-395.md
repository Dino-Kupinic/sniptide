# WRK-395 validation

2026-10-28. The response snapshot, durable counter, list projection and admission fixes are implemented and independently reviewed. The old memory ceilings are removed. High-load latency and transport gates are **not uniformly passing**.

## Runtime and method

Baseline: `63665a78a43ef5732294f5eac83b765ef3147c19`. Matched snapshot/mixed build: `3e39bdf`. Final keepalive build: `5e043faa71fa1678adaa7799ed195b612628274e`. Later report commits do not change application behavior.

Node 24.22.1 runs the production standalone server on macOS ARM64 with normal Node heap sizing. The app has no forced 384 MiB cap. PostgreSQL 17 runs in a task-owned Docker container with 768 MiB allocated inside Docker's approximately 3 GiB, three-CPU VM. The host has eight logical CPUs and 16 GiB RAM. App, generator and other desktop applications share the host. Preview-video generation is disabled for both builds.

The dataset begins with 100,000 synthetic pastes across 40 accounts, including a 10,000-paste account. Separate correctness fixtures add a small number of rows. Both builds use the same database and additive schema. Each mixed sample has 15 seconds at five requests/sec, followed by 20 measured seconds at 20 requests/sec. Five paired repeats alternate AB and BA ordering; each build starts in a fresh process. Mixed reads cover share/raw pages, list/search/cursors, collections, dashboard and deep pagination. These are HTTP checks, not full browser navigation. The hot profile uses a browser-like user agent and exercises ordinary view counting, with 20 serial warmup reads before measurement.

## Overload and recovery

The final transport fix removes forced Connection: close on early refusals. Real HTTP Agent regressions fail before that fix and pass afterward for repeated GET and 128 KiB POST rejections and recovery on the same socket.

At 200 requests/sec, unexpected failures fall from 503 to zero after the keepalive fix. At 400, they fall from 4008 to 756, but transport failures and latency violations remain. This is **not a 400 requests/sec capacity pass**. The server remains alive. Runtime counters record peaks of 64 ordinary HTTP requests, 10 pool execution permits and 64 waiting submissions. RSS was sampled about every two seconds; no hard memory bound or absence of leaks is established. Node regression tests cover refusal after streamed headers; every sampled runtime lateDatabaseRejected counter is zero. Successful hot responses pass fixture-content checks. The 500 ms p95 / 1000 ms p99 targets are intentionally retained; their failed outcomes are not relabeled as passes.

The three-minute recovery soak at ten requests/sec passes every gate: p95 110.2 ms, p99 356.3 ms, zero unexpected statuses and zero dropped iterations. The final post-keepalive recovery probe also passes, with p95 66.1 ms.

## Deployment and remaining limits

Normal views and milestone notifications become visible after durable batches drain. Burns remain synchronous and atomic. Queue health is sampled per process and is not a hard global disk bound. HTTP admission defaults to 64 ordinary requests, two probes and 128 live streams; DB execution is bounded by the configured pool with a finite 64-submission queue.

The memory cap removal does not clear saved Coolify resource values. Clear old NODE_OPTIONS and container memory overrides when redeploying. The new migration backfill can block writes; back up and plan the upgrade window. No production deployment or merge was performed.

Further capacity work needs an isolated staging host and target latency/traffic budgets. The remaining high-load failures are reported, not claimed fixed. Raw summaries, server snapshots and scripts are retained in the local artifact directory beside this report. No production traffic or third-party systems were stressed.
